Prinsip Keamanan & Batasan Pengujian

Seluruh simulasi di bawah ini menggunakan data sintetis lokal dan tidak melakukan serangan aktual ke sistem manapun. Tujuan modul ini adalah mendemonstrasikan secara visual mekanisme kegagalan otorisasi versus mekanisme kontrol otorisasi yang benar untuk keperluan Laporan Audit KSI M5–M6.

🔓

Kerentanan 1: IDOR (Kontrol Akses Objek Lemah)

Insecure Direct Object Reference pada Permintaan Data Nilai
CWE-639

Deskripsi Masalah: Aplikasi menerima parameter identitas objek (seperti student_id) dari peramban, lalu mengembalikan data tanpa memeriksa apakah pengguna yang sedang login berhak atas objek tersebut.

Pengguna Saat Ini: mhs001 (Ahmad Fauzi) Objek Target Sintetis: mhs002 (Siti Nurhaliza)
Hasil Pengujian Simulasi IDOR: Belum Dijalankan

Klik salah satu tombol di atas untuk menjalankan pengujian dan melihat respons kontrol akses.

💡 Rekomendasi Perbaikan:

Jangan mempercayai ID objek dari client. Validasi kepemilikan objek pada sisi backend berdasarkan sesi terverifikasi pengguna (misal: session.user.id === requested_resource.owner_id).

⚡

Kerentanan 2: Eskalasi Hak Akses (Privilege Escalation)

Manipulasi Parameter Peran Pengguna pada Sisi Klien
CWE-269

Deskripsi Masalah: Terjadi ketika sistem mempercayai atribut hak akses seperti peran (role: "admin") yang dikirim atau dimanipulasi dari browser pengguna tanpa verifikasi otoritatif pada sisi server.

Peran Asli Akun: mahasiswa Peran yang Diklaim: admin
Hasil Pengujian Eskalasi Hak Akses: Belum Dijalankan

Klik salah satu tombol di atas untuk menguji respons sistem terhadap manipulasi peran.

💡 Rekomendasi Perbaikan:

Otorisasi wajib ditegakkan secara absolut pada server (RBAC/ABAC). Peran harus diambil dari sesi terenkripsi atau token JWT ber-tanda tangan digital yang divalidasi ke database otoritatif.
